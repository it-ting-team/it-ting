# 작업 계획서와 완료 보고서

코드를 쓰기 전에 무엇을 어떻게 만들지 정해 승인을 받고, 끝나면 무엇을 했는지 같은 문서에 남긴다. 사람, Claude Code, Codex가 같은 방식으로 일한다.

## 언제 쓰나

| 작업 | 계획서 |
|---|---|
| 코드나 설정을 바꾸는 기능 · 설정 티켓 | 쓴다 |
| 문서만 바꾸는 작업 | 쓰지 않는다 |
| 한두 줄 고치는 작업(오타, 작은 버그) | 쓰지 않는다 |

## 하지 말 것

- MUST NOT: 계획을 승인받기 전에 코드를 바꾸지 않는다. 계획서 파일을 쓰는 것과 브랜치를 만드는 것은 괜찮다.
- MUST NOT: 이미 정해진 것(명세, 이전 작업, 대화에서 정한 것)을 다시 묻지 않는다.
- MUST NOT: 명세에 없거나 "미정"인 것을 혼자 정하고 넘어가지 않는다. 계획의 "이번에 정할 것"에 올려 승인을 받는다.
- MUST NOT: 계획만 따로 커밋하거나 Draft PR을 열지 않는다. 계획은 로컬 파일로 검토하고, 결과와 함께 PR에 들어간다.

## 절차

### 1. 티켓과 브랜치

1. Jira 티켓을 확인한다. 없으면 사용자에게 알리고, 만들어도 되면 만든다.
2. 최신 `origin/dev`에서 브랜치를 만든다. 이름은 `docs/branch-strategy.md`를 따른다.

   ```bash
   git fetch origin
   git switch -c <유형>/<영역>/KAN-<번호>-<설명> origin/dev
   ```

### 2. 문서 읽기

`AGENTS.md`의 "작업 전에 읽을 문서" 표에 따라 읽는다. API 작업이면 같은 번호의 세 문서를 함께 읽는다.

- `docs/spec/<번호>-*.md`: 무엇을 만드는가
- `docs/api/<번호>-*.md`: 어떻게 주고받는가. 끝의 "구현 단계로 넘기는 것"
- `docs/db/<영역>.md`: 무엇을 저장하는가. "미정"인 칸
- 이전 작업 기록 `docs/work/KAN-*.md`: 같은 영역에서 정한 것

### 3. 미정 사항 모으기

1. 읽은 문서에서 "미정", "구현 단계로 넘기는 것", "(제안)"을 모두 찾는다.
2. 이번 작업에 필요한 것만 고른다.
3. 각각 제안과 까닭을 정한다. 실제 값으로 예를 든다.
4. 하나씩 따로 묻지 않고 계획서의 "이번에 정할 것"에 모은다.

### 4. 계획 쓰기

1. `docs/work/_template.md`를 `docs/work/KAN-<번호>.md`로 복사한다.
2. "계획" 절을 채운다: 목표, 범위 밖, 정한 것, 이번에 정할 것, 만들 것, 테스트.
3. "결과" 절은 비워 둔다.

### 5. 승인 받기

1. 사용자에게 계획서 경로와 요약을 보여 준다. 요약에는 "이번에 정할 것"의 각 항목을 넣는다.
2. 고를 것이 있으면 항목마다 선택지와 추천을 보여 주고 답을 받는다. 추천안을 첫 번째에 둔다.
3. 받은 답을 "정한 것" 표로 옮기고 정한 사람과 날짜를 적는다.
4. 사용자가 "진행", "시작"처럼 승인하면 구현한다.

### 6. 구현

- `AGENTS.md`의 규칙을 따른다.
- 계획과 다르게 해야 하면 기록해 둔다. 명세와 달라지면 코드를 바꾸기 전에 묻는다.

### 7. 결과 채우기

1. "결과" 절을 채운다: 한눈에 보기, 바꾼 것, 확인한 것, 계획과 달라진 점, 남은 일, 검토 순서.
2. "한눈에 보기"에 Mermaid 다이어그램을 넣는다.

   | 작업 | 다이어그램 |
   |---|---|
   | 모든 기능 작업 | 흐름도(`flowchart`) 하나. 요청이 지나가는 길이나 처리 단계, 응답이 갈리는 곳은 마름모 |
   | 순서가 중요한 처리(로그인, 가입처럼 여러 단계) | 시퀀스(`sequenceDiagram`) |
   | 테이블을 만들거나 바꿈 | ERD(`erDiagram`). 새로 만든 테이블과 읽기만 하는 테이블을 글로 구분 |

   - 라벨에 특수문자나 줄바꿈이 있으면 `"..."`로 감싸고 줄바꿈은 `<br/>`로 쓴다.
   - 예: `docs/work/KAN-38.md`의 "한눈에 보기"

3. "계획과 달라진 점"에는 계획에 없던 것과 혼자 판단한 것을 모두 적는다.

### 8. PR

스킬 `pr-create`로 PR을 만든다. PR 본문 맨 위에 "한눈에 보기"를 같이 넣는다.

## 끝났는지 확인

- [ ] 계획을 승인받은 뒤 구현했다.
- [ ] "이번에 정할 것"의 답이 모두 "정한 것"으로 옮겨졌다.
- [ ] 정한 값이 `docs/api/`, `docs/db/`의 "미정" 칸에도 적혔다.
- [ ] "결과"의 모든 절이 채워졌고 "한눈에 보기"에 다이어그램이 있다.
- [ ] "계획과 달라진 점"이 비어 있지 않거나 "없음"이라고 적혀 있다.
